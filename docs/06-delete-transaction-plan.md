## 2. 本阶段学习目标

- `defineEmits`：子组件通过事件请求删除。
- 事件参数：用唯一 ID 指定操作对象。
- 多层组件事件转发：单条账单 → 列表 → 页面。
- `find`：定位需要确认的账单。
- `filter`：生成不包含目标账单的新数组。
- 通过 `ref.value` 替换数组，触发列表和 computed 更新。
- 不可变操作：不在子组件中修改 props，不手动删除 DOM。
- 理解自定义组件事件不会像原生 DOM 事件一样自动向祖先冒泡。

继续使用现有 Vue 能力，不引入依赖。

## 3. 交互约定与范围

| 项目 | 本阶段约定 |
|------|------------|
| 删除入口 | 每条卡片提供始终可见的普通删除按钮 |
| 确认方式 | 使用浏览器原生 `window.confirm`，展示目标分类与金额 |
| 确认删除 | 只删除指定 ID 对应的账单 |
| 取消删除 | 列表、预算、账单顺序不变 |
| 无效 ID 或不存在的账单 | 安静忽略，不弹确认、不修改数组 |
| 删除后顺序 | 剩余账单的相对顺序不变 |
| 删除最后一条 | 显示现有空状态，总支出和预算百分比为 0 |
| 删除后新增 | 仍能正常打开表单并保存新账单 |
| 持久化 | 暂无；刷新恢复代码中的示例账单 |

浏览器原生确认框是当前阶段的简单实现，文案与按钮外观可能因浏览器不同而不同。不新建 Vue 确认弹窗，避免把弹窗状态管理和删除基础逻辑混在一起。

暂时不做：

- 左滑、触摸手势、回弹和单行展开管理，留到 1.7。
- 撤销删除、回收站、批量删除。
- 删除动画、异步删除接口、保存中的等待状态。
- `localStorage`、Pinia、数据同步。
- 账单编辑、预算修改和分类统计。

没有撤销能力，所以先通过明确的确认步骤降低误删风险。

## 4. 状态与职责

| 组件 | 本阶段职责 |
|------|------------|
| `TransactionItem.vue` | 展示删除按钮，发出 `delete` 事件及 `transaction.id` |
| `TransactionList.vue` | 监听子项事件，显式转发 `delete` 和 ID |
| `App.vue` | 验证 ID、查找账单、确认删除、更新数组 |
| `BudgetHeader.vue` | 不变，通过 props 展示新的预算计算结果 |
| `EmptyState.vue` | 不变，在数组为空时显示 |

子组件不能直接改账单数组。确认操作也放在 `App.vue`，让“确认后更新数据”集中在同一个入口。

事件名称统一为 `delete`，参数统一为数字 ID，不混用数组下标、金额或整条账单对象。

## 5. 完整数据流

```text
TransactionItem.vue
    emit('delete', transaction.id)
        ↓
TransactionList.vue
    @delete → emit('delete', id)
        ↓
App.vue
    @delete → deleteTransaction(id)
        ↓
ID 检查 → 找到目标 → window.confirm
        ↓ 确认
transactions.value = transactions.value.filter(...)
        ↓
TransactionList 重新渲染
        +
totalExpense、budgetPercent 自动重新计算
```

注意：如果列表没有监听并转发事件，`App.vue` 不会自动收到孙组件发出的事件。

为什么用 ID 而不是下标？新增账单置顶或删除其他账单后，下标会变化。ID 表示账单身份，正好与现有 `v-for` 的 `:key="transaction.id"` 一致。

## 6. TransactionItem.vue 的计划修改

### 6.1 声明事件

保留现有 props，新增：

```js
const emit = defineEmits(["delete"]);
```

### 6.2 增加可见入口

计划把原金额区域包装为右侧操作列：

```vue
<div class="transaction-right">
  <div class="transaction-amount" :class="transaction.type">
    {{ transaction.type === "income" ? "+" : "-" }}¥{{ transaction.amount.toFixed(2) }}
  </div>
  <button
    type="button"
    class="transaction-delete"
    :aria-label="`删除${transaction.category}账单，金额${transaction.amount.toFixed(2)}元`"
    @click="emit('delete', transaction.id)"
  >
    删除
  </button>
</div>
```

按钮文本保持“删除”，可访问名称补充分类与金额。它是普通 button，可通过键盘激活，不把整个账单卡片设为删除入口。

如果两条账单分类和金额相同，按钮可访问名称可能相同；业务仍按各自 ID 区分，测试应定位目标卡片后操作其按钮，而不是假设名称唯一。

### 6.3 处理旧背景层与布局

- 移除当前不可操作的 `<div class="delete-btn-bg">删除</div>` 及对应样式，避免同一张卡片存在两套删除视觉入口。
- 不启用现有的滑动或动画样式，不提前绑定触摸事件。
- 新增 `.transaction-right` 纵向排列金额和按钮，右对齐，`flex-shrink: 0`。
- 左侧内容设置 `min-width: 0`，文字列对长备注做换行或截断，避免窄屏把按钮挤出卡片。
- 按钮使用现有危险色变量，点击区域至少 `44 × 44` CSS 像素，增加可见键盘焦点样式。
- 不修改全局样式、颜色变量或其他组件。

1.7 再设计真正的滑动操作层。删除业务入口与事件约定届时保持不变，只调整按钮如何显示。

## 8. App.vue 的计划修改

### 8.1 接入事件

```vue
<TransactionList
  :transactions="transactions"
  @delete="deleteTransaction"
/>
```

### 8.2 删除处理函数

```js
function deleteTransaction(id) {
  if (!Number.isSafeInteger(id) || id <= 0) {
    return;
  }

  const target = transactions.value.find(
    (transaction) => transaction.id === id,
  );
  if (!target) {
    return;
  }

  const confirmed = window.confirm(
    `确定删除这笔${target.category}账单（¥${target.amount.toFixed(2)}）吗？此操作无法撤销。`,
  );
  if (!confirmed) {
    return;
  }

  transactions.value = transactions.value.filter(
    (transaction) => transaction.id !== id,
  );
}
```

步骤：

1. 拒绝字符串 ID、非整数、非正数或超出安全整数范围的值。
2. 找不到账单时直接返回，避免空操作也弹出确认框。
3. 用当前账单的分类和金额生成提示，不依赖子组件传来的描述。
4. 取消时直接返回，不赋新数组。
5. 确认后使用严格比较过滤目标 ID。

当前账单 ID 在内存中唯一，因此只会移除一条。如果将来加载外部数据出现重复 ID，必须在数据载入阶段验证或修复；这里不把 `filter` 当作重复 ID 处理方案。

不要采用：

```js
// 不根据数组位置或金额删除
transactions.value.splice(index, 1);

// 不在组件里直接操作页面节点
// element.remove();
```

`splice` 本身可以是合法响应式操作；这里只选择按 ID 的 `filter`，以让删除意图更清楚，避免位置变化导致删除错项。

### 8.3 预算更新

保持 1.5 的整数分累计与百分比 computed，不手动减总支出：

```text
transactions 改变
    ↓
totalExpense 自动重新计算
    ↓
budgetPercent 自动重新计算
    ↓
BudgetHeader 自动更新
```

以现有示例为基线：

| 操作 | 总支出 | 百分比（预算 3000） |
|------|--------|--------------------|
| 初始两条：256 + 123 | 379.00 | 13% |
| 删除 ID 1 的 256 元 | 123.00 | 4% |
| 再删除剩余 123 元 | 0.00 | 0% |
| 空列表新增 100 元 | 100.00 | 3% |

取消确认时仍是 379.00 和 13%。

### 8.4 与新增 ID 策略的关系

1.5 使用“现有最大 ID + 1”。因此：

- 删除后新增，ID 必须与所有当前保留账单不同。
- 删除最大 ID 或清空后，之前用过的 ID 可能再次使用。
- 当前无异步请求、持久化或历史引用，允许这种复用；不把“当前唯一”说成“永不复用”。

重复请求删除已不存在的 ID 时，忽略即可。未来引入持久化、异步删除或撤销时，需要重新设计长期稳定的 ID 和操作关联。

## 13. 常见问题与复盘

### 为什么现有“删除”文字不算完成删除入口？

它在卡片后面，没有滑动逻辑露出，也没有事件处理。视觉残留不等于可操作功能。本阶段先建立真实按钮，后续再完善左滑展示。

### 为什么 TransactionList 必须转发事件？

它位于账单项和 App 之间。Vue 自定义组件事件不会自动一路冒泡，必须在每层明确接线。

### 为什么确认框放在 App 而不是按钮组件？

App 拥有账单数据，可以确认目标仍存在，并把确认与实际修改放在同一个业务入口。以后替换确认方式时也不需要改每张卡片。

### 为什么删除以后不用手动减金额？

总支出由 computed 从数组派生。手动减总额会多出一个必须同步维护的数据源，容易与数组不一致。

### 为什么不直接把左滑一起做？

按 ID 删除是数据操作，左滑是手势与展示状态。先验证删除正确，再实现手势，可以更容易定位问题，也避免学习内容一下子过多。

### 删除后刷新怎么又出现账单？

当前是内存状态。只有到 1.8 把新增和删除结果保存到本地存储，刷新才能保留这些变化。
